# 项目决策

## D-001 独立新项目，不在稳定应用上直接大改

- 状态：`accepted`
- 决策：平台在独立目录和独立 Git 仓库开发；现有虚谷作战地图保持稳定，只作为迁移来源和验收样本。
- 原因：平台化涉及数据模型、权限、存储和 UI 壳重构，直接在稳定应用上施工会增加回退和数据风险。

## D-002 平台—项目—作战单元三级结构

- 状态：`accepted`
- 决策：平台管理多个项目；每个项目内部管理多个作战单元或团队。

## D-003 固定模块加模板，不做任意代码低代码

- 状态：`accepted`
- 决策：低代码能力来自固定模块、版本化 Schema、项目模板和结构化数据；LLM 不生成或执行页面代码。

## D-004 LLM 只生成增量提案

- 状态：`accepted`
- 决策：LLM 输出带 `projectId`、`baseVersion` 和证据的 `ChangeProposal`；管理员审核后合并到草稿，人工发布。

## D-005 首版采用 SQLite

- 状态：`accepted`
- 决策：首版单服务器使用 SQLite 提供事务、索引和迁移；多机部署需求出现后再评估 PostgreSQL。

## D-006 当前虚谷项目是首个迁移项目

- 状态：`accepted`
- 决策：稳定 ID 为 `xugu-agentic-group`，迁移必须保持七个作战单元、路线、任务、甘特和成果语义。

## D-007 使用 Node.js 内置 SQLite 接口

- 状态：`accepted`
- 决策：平台最低运行时提高到 Node.js 24.15，使用内置 `node:sqlite` `DatabaseSync`。
- 原因：保持单服务器部署简单，避免原生 npm 数据库驱动的编译和交付差异，同时通过仓储边界保留未来更换驱动或 PostgreSQL 的可能。
- 影响：新平台不再兼容 Node.js 18；参考虚谷应用保持原有 Node.js 18 兼容性且未被修改。

## D-008 版本子图规范化存储

- 状态：`accepted`
- 决策：项目保存指向 `published` 和 `draft` 的独立版本指针；作战单元、路线、任务、依赖和战线按版本使用独立表存储。
- 原因：确保项目隔离、关系约束、事务更新和未来发布/回滚不依赖单一巨型 JSON。

## D-009 服务端摘要会话与内存 CSRF

- 状态：`accepted`
- 决策：使用随机 Cookie 会话，数据库只保存 token 摘要；Cookie 为 HttpOnly、SameSite=Strict，CSRF token 只进入页面内存。
- 原因：避免将可重放凭据暴露给 JavaScript 或 Web Storage，并同时覆盖会话固定、跨站写请求和浏览器后退缓存风险。
- 影响：首版采用 30 分钟空闲与 8 小时绝对过期；HTTPS 部署必须启用 Secure Cookie。

## D-010 平台壳只使用本地固定组件

- 状态：`accepted`
- 决策：Phase 2 使用仓库内语义 HTML/CSS/JavaScript，不引入远程 UI registry、CDN、项目提供的组件或内联可执行资源。
- 原因：平台与项目内容边界必须清晰，且当前阶段不应提前形成任意代码低代码入口。

## D-011 多项目平台沿用 Xugu 桌面界面骨架

- 状态：`accepted`
- 决策：桌面端以 Xugu 稳定应用的白色顶部导航、暖色指挥背景、左目标/右战况 Hero 和纵向章节卡片为平台基线；多项目能力只增加项目入口、切换器、筛选和管理控件。
- 原因：用户明确要求新平台与 Xugu Agentic Group Schedule 界面基本一致，通用 SaaS 侧栏会破坏已有认知和迁移连续性。
- 影响：响应式仍作为兼容回退，但不能反向主导桌面信息结构；Phase 3 固定模块继续在同一 Xugu 视觉框架中扩展。

## D-012 项目表现文案由模板和术语配置驱动

- 状态：`accepted`
- 决策：项目详情的顶部标题、Banner、当前状态提示、事实标签、模块标签和新建摘要由项目模板与结构化术语配置决定，不使用全平台硬编码的 Xugu 文案。
- 原因：平台需要管理不同类型项目，同时保留 `xugu-agentic-group` 作为首个 Xugu Agentic Group Schedule 作战项目的界面连续性。
- 影响：标准项目使用团队、任务、里程碑和交付物语言；作战项目使用作战单元、行动任务、战役节点和战果语言。配置只能选择固定预设，不得提供项目级页面代码。

## D-013 版本化目录与固定九模块渲染边界

- 状态：`accepted`
- 决策：模板以不可变的 `templateId@version` 目录发布，模块数据以显式 `schemaVersion` 与 allowlist `viewVariant` 交换；服务端只注册九种模块，浏览器只使用仓库内固定 renderer map。
- 原因：同一平台需要表达 Xugu 作战项目和标准项目差异，同时阻止项目数据、材料或未来 LLM 输出选择组件路径或执行页面代码。
- 影响：模板可配置术语、主题、字段、状态、模块顺序/启停和已批准视图；未知模板、类型、Schema、视图和可执行内容全部失败关闭。模块配置只写草稿，发布仍留给后续审核发布阶段。

## D-014 项目证据采用本地确定性检索与显式授权

- 状态：`accepted`
- 决策：首版材料使用项目隔离的本地对象目录、SQLite 关系与 FTS5；证据只有在处理成功、属于当前代际且获得项目问答授权时才进入检索。provider 默认禁用，只接收受控上下文且不得调用工具。
- 原因：单服务器内部试用需要无外部密钥也可完整验证，并必须把跨项目泄漏、提示注入、伪造引用和处理失败控制在可重复测试的事务边界内。
- 影响：材料原件和运行产物不进入 Git；可选扫描/OCR/PDF 工具通过有界适配器接入。问答只能返回 allowlist 引用并保持只读，更新意图在 Phase 4 仅作为元数据。

## D-015 生成任务锁定证据清单且提案独立验证后保存

- 状态：`accepted`
- 决策：每个 generation task 在创建时锁定 `projectId`、当前发布版本、同模板材料、当前提取代际、证据 ID/哈希和 Schema；provider 只能返回相同 envelope 下的结构化增量。服务端在持久化前独立执行 Schema、项目/证据、模板字段、目标、语义、日期、依赖 DAG、重复和版本冲突校验。
- 原因：模型输出和材料正文都不可信，只有服务器拥有授权、当前版本、固定模块和事务边界；把锁定输入、provider 调用和验证提案分离可以确定性阻断跨项目引用、旧证据、stale base 与模型越权。
- 影响：仅完整通过的 pending proposal 与规范化 item/evidence 关系原子保存；失败任务保留稳定状态、attempt、Token/成本聚合且不留部分提案。generation provider 配置与 chat 独立，默认禁用；Phase 5 没有任何 draft/published 写路径。

## D-016 审核决定独立保存且草稿合并采用 copy-on-write

- 状态：`accepted`
- 决策：提案项保持不可变，人工决定、编辑字段、说明与审核人保存到独立审核实体；合并从当前草稿复制新版本，应用所有接受项并完成完整图校验后才切换草稿指针。
- 原因：需要同时保留模型原建议、人工修订和可审计决定，并确保任一字段、关系或存储失败都不污染现有草稿。
- 影响：接受不等于合并，合并不等于发布；非法编辑在保存阶段重新验证，事务失败不产生部分版本或指针变化。

## D-017 发布创建新版本和草稿基线，回滚只走直接前驱

- 状态：`accepted`
- 决策：发布只复制当前草稿为新的不可变发布版本，并从其创建新的草稿基线；回滚只能指向当前发布事件记录的直接前驱。
- 原因：显式版本链比覆盖式更新更容易审计、恢复和隔离，并阻止客户端选择任意历史版本造成状态跳跃。
- 影响：发布/回滚必须由项目管理员或平台管理员确认，携带 CSRF，并写 `publication_events` 与追加式审计；提案不存在直达发布路径。

## D-018 SQLite 备份使用一致快照并离线恢复

- 状态：`accepted`
- 决策：运行备份使用 SQLite `VACUUM INTO` 产生一致文件；恢复前验证 quick check、外键和最低迁移版本，恢复要求应用离线并先保存目标数据库备份。
- 原因：直接复制 WAL 数据库文件可能得到不一致快照，在线覆盖运行数据库会破坏连接与事务状态。
- 影响：备份和恢复通过服务端脚本执行，运行数据库、上传原件和备份文件均不进入 Git。

## D-019 作战单元生命周期采用版本化状态，不做物理删除

- 状态：`accepted for Phase 7`
- 决策：作战单元/团队新增、归档和退出都作为带证据的版本化提案进入审核；归档和退出通过 `active / archived / exited` 生命周期状态表达，不从历史版本中物理删除。
- 原因：作战单元承载任务、甘特、战线、成果和证据链，物理删除会破坏历史发布版本、审计和材料来源解释。
- 影响：归档或退出前必须校验未完成任务、依赖、战线和甘特引用；如仍有活跃引用，提案必须同步迁移、关闭或归档相关任务，否则阻止接受或合并。

## D-020 发布前运维采用本地 request trace 与脱敏诊断包

- 状态：`accepted for Phase 7`
- 决策：每个 HTTP 请求、后台材料任务、生成任务、审核合并和发布事件都生成或继承 request/trace ID；未知异常和后台失败保存脱敏堆栈、错误指纹和关联上下文，并提供管理员诊断包。
- 原因：准备对外发布时，用户可上报一个稳定编号，管理员能定位堆栈、作业、提案和发布上下文，同时不能泄露 Cookie、CSRF、密钥、材料正文或模型提示词。
- 影响：普通用户只看到报障编号；平台管理员或授权项目管理员才能查看诊断信息。产品内测试中心必须覆盖 trace、错误事件和诊断包权限边界。

## D-021 路线图采用多视图工作台，卡片移动仍走结构化提案

- 状态：`accepted for Phase 8`
- 决策：路线模块不再只承担单一曲线节点展示，而是提供固定、可切换的活动路线图、阶段卡片板、作战单元进度和依赖网络四种投影。活动路线图采用以时间列为主的活动、目标、任务表达；阶段卡片板采用状态泳道与可拖拽任务卡。所有视图均读取同一受控版本化数据并保持对象深链。
- 原因：用户需要同时看到战略阶段、多作战单元分支、执行进度和材料更新后的待审核变化；当前曲线主图适合概览但不适合承载密集的多任务协作，也不能把点击结果隐藏到页面底部。
- 影响：路线、单元、任务和 proposal item 必须有一致的稳定 ID、选中态和就地详情。拖拽、状态推进、负责人/日期调整不得绕过 `ChangeProposal`、审核、copy-on-write 草稿合并与人工发布；这不是任意看板编辑器，也不允许项目注入前端代码。

## D-022 分形作战生命周期与主副泳道双锚点模型

- 状态：`accepted`
- 决策：路线图与作战推进采用一套通用范式——
  - **分形生命周期**：项目层面分 事前（准备）/事中（当前）/事后（已交付）三带；每个作战单元在执行阶段也各自走自己的完整阶段动作（研发、销售、服务等链路同理），生命周期范式可分形下沉到作战单元。
  - **主副泳道**：一条主泳道（阶段时间轴）承载战略与阶段；多条作战单元副泳道（甘特任务条）承载分工与并行子任务。
  - **双锚点**：主→副拆解用"拆解锚点"（阶段起点，表达项目锚点·任务拆解起点）；副→主收口用"收口锚点"（由 `closures.between` 两端阶段中点生成）。
  - **多次拆解合并**：一个阶段可多次向下拆解出子任务，多个子任务/单元可合并收口；一个作战单元同一时间可并行多个子任务，符合真实项目推进时目标持续变化的形态。
- 原因：真实项目推进时目标持续变化，路线图会经历多次任务拆解与合并；固定生命周期范式 + 双锚点让"看战略、看分工、看推进、看收口"在统一模型里自洽，且生命周期可分形下沉到作战单元，避免只有项目级视角。
- 影响：Phase 8 泳道视图（`?view=swimlane`）已用纯投影层落地范式可见表达（三带/主副泳道/双锚点/并行子任务），但拆解关系仍靠任务→阶段窗口归属投影推断；后续 Phase 9 把拆解关系、单元级分形、术语模板化、多次拆解合并落到数据、提案与模板层，仍不绕过审核直写 draft/published。

## D-023 parentId 拆解关系限于同作战单元（方向 A）

- 状态：`accepted for Phase 9`
- 决策：`parentId` 只表达**同作战单元内**的主任务→子任务拆解；跨作战单元的"阶段拆解"由阶段本身作为项目锚点表达（落在该阶段窗口内的各单元任务都是它的拆解产物）。validator 禁止跨单元 parentId 的既有约束保持不变。
- 原因：LIF-04 要求阶段拆解出子任务分发到不同作战单元，但 `project-validator.mjs` 硬性禁止跨单元 parentId。放开约束（方向 B）需引入无 unit 的"拆解根任务"，打破"每个 task 必须属于一个 unit"不变式，风险大。方向 A 不破坏既有约束、改动最小、符合 D-022"拆解锚点是阶段起点"语义。
- 影响：拆解关系从"时间窗口归属推断"升级为"显式 parentId"，但仅限同单元；跨单元拆解仍由阶段锚点隐式表达。后续若需显式跨单元拆解树，再评估放开约束。

## D-024 单元级生命周期采用投影派生，不加独立 stage 集（方向 Y）

- 状态：`accepted for Phase 9`
- 决策：作战单元的生命周期带（事前/事中/事后）由该单元自己的任务状态/progress/日期派生，不给 unit 加独立 stage 序列或 unit-stages 子表。
- 原因：方向 X（unit 加独立 stage 集）与项目级 stage 窗口语义重叠，真实数据无独立 unit-stage 定义，数据模型扩展大。方向 Y 符合"分形"本质——同一范式下沉到 unit 层（由任务演进派生），而非给每 unit 造独立 stage 体系；零数据模型扩展。
- 影响：unit 级带是纯投影派生，不引入新数据字段、不进 DTO、不改 loadUnits。派生规则用既有 task 的 state/progress/日期，无新状态机。

## D-025 卡片泳道即项目路线图，退役独立活动路线

- 状态：`accepted`
- 决策：A 卡片泳道成为 Roadmap 模块的项目路线图主视图，不再并列提供独立“活动路线图”曲线视图。路线图切换器保留项目路线图、阶段卡片板、作战单元进度和依赖网络；旧 `?view=timeline` 与未知 view 兼容回落到项目路线图。
- 原因：用户确认主任务时间线、按作战单元展开的副任务卡片及其收口本身已经完整表达项目路线；再保留一张独立曲线会重复表达同一结构并争夺认知入口。
- 影响：删除 timeline 路由投影、SVG 路线节点和模块检查器的产品入口与实现；`stage/unit/task/anchor` 深链继续由卡片路线图承载。阶段卡片板、单元进度、依赖网络和独立甘特模块仍作为执行、比较、依赖和精确工期的辅助视图，不改变 published/draft/proposal 边界。

## D-026 九类基础模块收敛为六个一级工作区

- 状态：`accepted`
- 决策：底层继续保留 Overview、Units、Roadmap、Task Network、Gantt、Outcomes、Risks、Metrics、Materials 九类固定安全模块；用户一级导航只呈现总览、项目路线图、作战单元/团队、排期甘特、项目健康和项目资料六个工作区。Task Network 不再单列，统一由 Roadmap 的依赖网络投影承载；Risks 与 Metrics 作为项目健康二级入口；Outcomes、材料台账与更新提案作为项目资料二级入口。
- 原因：九个模块按技术实体平铺会把推进、协作、治理和沉淀混在同一层；Task Network 与 Roadmap 依赖网络读取相同任务依赖图，风险/指标在当前项目均为空但各占一级入口，成果与材料又缺少证据关系上的信息架构归属。
- 影响：导航是显示层分组，不删除模块注册、API、数据库、模板配置、角色授权或既有深链。模块配置仍管理九类底层模块；六个工作区会根据当前发布版已启用模块自动出现，健康和资料二级导航只暴露可访问模块。页面显示名称统一为“项目路线图”“排期甘特”“项目资料”。

## D-027 单进程部署随 Web 服务启动材料处理 Worker

- 状态：`accepted`
- 决策：当前单服务器部署由 `server.mjs` 在完成迁移和管理员初始化后启动一个串行材料处理 worker；启动时恢复遗留任务，空闲时轮询，异常时退避，进程退出时先停止 worker 再关闭数据库。
- 原因：材料上传是 UI 的异步工作流，生产启动入口此前只提供 HTTP 服务，未消费已经进入队列的材料任务；测试 fixture 自行运行 processor 掩盖了真实启动缺口。
- 影响：正式 UI 上传无需额外后台命令即可从队列进入证据就绪。当前仍坚持单 worker、同一 SQLite 事务域；未来多进程部署必须先引入可证明的租约/并发协调，不得直接复制本 worker。

## D-028 真实 LLM 使用精确输出契约与服务端密钥配置

- 状态：`accepted`
- 决策：OpenAI-compatible generation provider 可通过服务端环境变量配置 base URL、模型、超时和 allowlist 内的 reasoning effort；API Key 只存在于忽略的本地环境文件或生产密钥设施。提示词必须携带精确的 `ChangeProposal` 根字段、change 字段、类型、枚举、ID、证据和警告契约，provider 输出仍由独立服务端 validator 失败关闭。
- 原因：真实 GLM-5.2 接入证明只描述“返回 JSON”不足以约束内部 Schema；模型思考输出和较大证据上下文也需要显式的有界配置。密钥和 provider 差异不得泄漏到浏览器、项目数据或版本库。
- 影响：provider-specific 参数只能来自服务端受控 allowlist，不能成为项目可执行配置。即使真实模型输出通过校验，也只能创建待审核提案；逐项审核、草稿合并和发布继续由独立人工 UI 动作完成。

## D-029 跨平台分发采用自带运行时与空数据默认

- 状态：`accepted`
- 决策：Windows/Linux portable 和 RPM 都打包固定 Node.js 运行时；RPM 使用 systemd 单服务部署。Release 通过运行文件白名单组装，默认不包含任何项目夹具、运行数据库、上传材料、日志、备份或密钥。全新数据库只有显式配置 `PLATFORM_SEED_FIXTURE` 才导入指定脱敏夹具。
- 原因：目标机器不应依赖预装 Node/npm，也不能把开发机的公司数据、真实 LLM 配置或运行状态带进 GitHub 与安装包；RPM 必须能用单条安装命令形成可管理服务。
- 影响：源码保留脱敏迁移夹具用于等价测试，但 GitHub Release 明确排除 `fixtures/`、`.planning/` 与 `test/`。RPM 数据落在 `/var/lib/ai-project-command-platform`，配置落在 `/etc/ai-project-command-platform`；portable 数据只写解压目录。多机、容器编排和 PostgreSQL 仍不在本次范围。

## D-030 项目创建支持三种入口（对话式、材料上传、手动表单）

- 状态：`accepted`
- 决策：项目创建提供对话式（AI 引导收集信息）、上传材料自动解析（提取项目骨架）、手动表单三种入口；手动表单保留当前方式。
- 原因：单一表单创建摩擦大，无法适应不同场景——有的用户手上有完整会议纪要可以直接喂系统，有的用户偏好对话逐步明确需求，有的用户只需要快速开空项目。
- 影响：对话式和材料上传创建需要新的引导流程和解析逻辑，但不改变项目实体、模板、权限和数据隔离。

## D-031 材料到更新流程去掉手动授权步骤

- 状态：`accepted`
- 决策：材料处理完成后无需手动"问答授权""生成授权"即可生成更新建议；界面不再出现"授权"概念；生成结果以卡片预览展示，确认即发布；删除卡片仍需手动操作。
- 原因：用户反馈授权步骤是多余的审批摩擦——问答是只读检索不应需要授权，生成是核心功能也不应需要手动开启；用户期望"上传→看到建议→确认→生效"一条直线。
- 影响：底层仍保留 AI 不得直写 draft/published 的安全边界；"确认发布"仍由人工触发。授权逻辑在数据层可保留（默认开启），但 UI 不再暴露为用户操作步骤。

## D-032 战情问答移到项目页面右侧独立浮动按钮

- 状态：`accepted`
- 决策：问答从材料工作区内部标签移出，改为项目页面右侧浮动按钮（类似咨询入口），点击展开问答面板。
- 原因：问答是跨工作区的通用能力（用户可能在看路线图时想问问题），不应藏在材料工作区二级标签里。
- 影响：材料工作区 localTabs 移除问答标签；项目壳增加浮动问答组件；问答 API 和只读边界不变。

## D-033 消除项目材料页面导航层级重复

- 状态：`accepted`
- 决策：项目资料二级导航与材料工作区内部 localTabs 不再重复出现同一层级入口；进入"项目材料"后直接显示内容，不再多一行标签。
- 原因：用户点击一级导航"项目资料"→二级"项目材料"后，页面内又出现"项目材料 | 战情问答 | 更新建议"一行标签，层级重复造成困惑。
- 影响：合并两组导航为一组；问答移出后材料工作区只剩"项目材料"和"更新建议"两个标签（问答已浮动化）；或进一步合并到二级导航。
