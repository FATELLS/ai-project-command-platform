# 系统 SPEC：AI 项目作战管理平台

状态：`canonical`

## 1. Mission

平台管理多个项目，每个项目管理多个团队或作战单元。用户通过固定工作区查看项目状态、路线、任务、甘特、风险、指标、成果和材料，并把会议纪要、计划、汇报、表格、图片等材料转化为有来源、可审核、可发布的结构化更新。

核心价值不是“让 AI 生成页面”，而是：

> 把项目内容更新从定制开发变成受控、可追溯、可回滚的数据变更流程。

## 2. Actors

| 角色 | 系统责任 |
|---|---|
| 平台管理员 | 初始化和管理平台、用户、全部项目、AI 配置和运维能力 |
| 项目管理员 | 管理指定项目成员、材料、审核、发布和回滚 |
| 项目编辑 | 上传材料、维护内容、生成和审核允许的更新 |
| 查看者 | 读取授权项目的已发布状态和允许的问答 |
| LLM Provider | 受限生成结构化建议或带来源回答，不是受信任主体 |
| 材料 Worker | 在同一 SQLite 事务域处理项目材料和证据 |

## 3. Core Objects

- `Project`：稳定项目身份、模板、状态和版本指针。
- `ProjectVersion`：不可变项目版本，属于 `published` 或 `draft` 层。
- `ProjectGraph`：模块、单元、阶段、卡片/任务、关系、战线、风险和指标。
- `Material`：项目归属明确的上传或人工材料。
- `EvidenceBlock`：可定位、带摘要和哈希的材料内容片段。
- `GenerationJob`：锁定基准版本、材料、证据、模板和 readiness 的生成任务。
- `ChangeProposal`：相对发布基准的结构化增量。
- `ReviewDecision`：独立于模型原建议的人工决定和编辑值。
- `PublicationEvent`：发布或回滚形成的追加式版本事件。
- `AuditEvent` / `OperationTrace`：权限动作和运行链路记录。

## 4. System Capabilities

### 4.1 平台与项目

- 登录、会话、强制改密和退出。
- 授权项目列表、搜索、最近访问和切换。
- 项目创建、编辑、归档和恢复。
- 用户与项目成员角色管理。

### 4.2 项目阅读与推进

- 固定九模块通过六个用户工作区呈现。
- 项目模板驱动术语、主题、模块、字段、状态和视图。
- 路线图、卡片板、单元进度、依赖网络和甘特读取同一版本图。
- 路线、任务、单元和锚点可深链定位。

### 4.3 材料与证据

- 接收受支持文件和人工文本。
- 校验容量、文件类型、签名、重复、频率、并发和解包限制。
- 异步提取可定位证据块。
- 按更新模板计算关键内容覆盖。
- 材料、证据、问答和生成均按项目隔离。

### 4.4 AI 问答与更新

- 问答只读取当前项目发布态和授权证据。
- 生成任务锁定当前发布版本、材料、证据和更新模板。
- LLM 输出只接受固定版本的结构化 `ChangeProposal`。
- 服务端独立校验 Schema、项目、证据、日期、依赖、重复和版本冲突。

### 4.5 审核与发布

- 单项接受、驳回、编辑后接受和模块级接受。
- 接受项通过 copy-on-write 事务合并到新草稿。
- 发布前比较 draft/published 并运行确定性检查。
- 人工发布创建新发布版本和新草稿基线。
- 回滚只允许当前发布事件的直接前驱。

### 4.6 运营与交付

- requestId/trace、脱敏错误事件和诊断包。
- 产品内核心自检。
- SQLite 一致备份和离线恢复。
- 脱敏项目迁移、导入导出和跨平台安装包。

## 5. Non-negotiable Invariants

1. 所有项目数据访问都由服务端按 `projectId` 和成员关系校验。
2. LLM 不得写 `draft`、`published` 或执行代码。
3. `proposal`、`draft`、`published` 三层不能合并为一个隐式状态。
4. 事实、完成状态和指标必须能回到证据。
5. 固定 renderer 负责页面；项目数据不能选择代码或组件路径。
6. 项目版本图通过完整校验后才能切换指针。
7. 审核决定不能覆盖模型原建议。
8. 发布和回滚必须由人工 capability、CSRF 和审计保护。
9. 密钥、材料原件、运行数据库和日志不得进入版本库或前端响应。
10. Xugu 项目稳定 ID、路线、任务、甘特和成果语义不得因平台演进丢失。

## 6. Quality Attributes

### Security

- HttpOnly/SameSite 会话 Cookie。
- 服务端摘要会话、CSRF、登录限流和统一越权 404。
- Provider 密钥服务端保存和响应脱敏。
- 材料和模型输入均视为不可信。

### Consistency

- SQLite 外键、触发器和显式事务保护跨实体关系。
- 发布、回滚和版本指针切换必须同成同败。
- 后台任务使用稳定状态、attempt 和幂等键。

### Auditability

- 登录、项目、成员、材料、生成、审核、合并、发布、回滚进入审计。
- 生成任务保存锁定证据和 readiness 快照。
- 生产故障可通过 requestId 关联诊断。

### Availability

- AI 或材料处理失败不影响已有项目浏览。
- Provider 默认可禁用；核心非 AI 工作区仍可使用。
- Worker 错误有界退避，不令 Web 进程静默退出。

### Portability

- 单服务器、SQLite、Node.js 运行。
- Windows/Linux portable 和 RPM 自带运行时。
- 默认安装不携带项目数据、材料或密钥。

### Usability

- 用户流程按任务而不是内部模块组织。
- 关键状态给出下一步。
- 移动端提供等价投影而不是删除内容。
- 技术 ID 和 Schema 不作为普通用户主界面。

## 7. Trust Boundaries

| 边界 | 信任规则 |
|---|---|
| Browser → HTTP | 所有输入不可信；服务端校验会话、CSRF、role/capability 和 projectId |
| Material → Extractor | 文件内容、压缩路径、文本和元数据均不可信 |
| Evidence → LLM | 证据作为带边界的不可信上下文，不允许工具调用 |
| LLM → Proposal | 输出必须经版本化 Schema 和领域校验 |
| Proposal → Draft | 只应用人工接受项，事务内完整图校验 |
| Draft → Published | 只允许人工发布，创建不可变新版本 |
| Runtime → Diagnostics | 必须脱敏凭据、材料正文和模型提示 |

## 8. Deployment Constraints

- 当前是单进程模块化单体。
- Web 服务与串行材料 worker 共享一个 SQLite 数据库。
- 不支持多进程并发 worker，除非先引入租约和并发协调 ADR。
- 运行目录、数据目录、上传目录、日志和备份由部署环境决定，不写入源码目录的发布白名单。

## 9. Out of Scope

- 任意拖拽页面生成器。
- LLM 生成或执行 HTML、JS、CSS、SQL、Shell。
- 无审核自动发布。
- 实时多人编辑和冲突合并。
- 多服务器分布式部署。
- 公共注册和匿名写入。

## 10. System Acceptance

- 新项目无需修改前端代码即可由固定模板创建和展示。
- 两个项目的材料、证据、问答、提案和版本不能串库。
- 典型材料可形成带来源的更新建议，并经人工审核发布。
- 无证据完成状态、循环依赖、跨项目引用和 stale 基准被确定性阻止。
- 任一生成、合并或发布失败都不破坏当前发布态。
- 发布后可审计并可回滚到直接前驱。
- 核心工作流在目标桌面和移动视口可完成。
- `npm run verify` 覆盖数据库、API、领域、安全、浏览器和分发基线。
