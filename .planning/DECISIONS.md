# 项目决策

## D-001 独立新项目，不在稳定应用上直接大改

- 状态：`accepted`
- 决策：平台在独立目录和独立 Git 仓库开发；现有虚谷作战地图保持稳定，只作为迁移来源和验收样本。
- 原因：平台化涉及数据模型、权限、存储和 UI 壳重构，直接在稳定应用上施工会增加回退和数据风险。

## D-002 平台—项目—作战单元三级结构

- 状态：`accepted`
- 决策：平台管理多个项目；每个项目内部管理多个作战单元或团队。

## D-003 固定模块加模板，不做任意代码低代码

- 状态：`accepted`
- 决策：低代码能力来自固定模块、版本化 Schema、项目模板和结构化数据；LLM 不生成或执行页面代码。

## D-004 LLM 只生成增量提案

- 状态：`accepted`
- 决策：LLM 输出带 `projectId`、`baseVersion` 和证据的 `ChangeProposal`；管理员审核后合并到草稿，人工发布。

## D-005 首版采用 SQLite

- 状态：`accepted`
- 决策：首版单服务器使用 SQLite 提供事务、索引和迁移；多机部署需求出现后再评估 PostgreSQL。

## D-006 当前虚谷项目是首个迁移项目

- 状态：`accepted`
- 决策：稳定 ID 为 `xugu-agentic-group`，迁移必须保持七个作战单元、路线、任务、甘特和成果语义。

## D-007 使用 Node.js 内置 SQLite 接口

- 状态：`accepted`
- 决策：平台最低运行时提高到 Node.js 24.15，使用内置 `node:sqlite` `DatabaseSync`。
- 原因：保持单服务器部署简单，避免原生 npm 数据库驱动的编译和交付差异，同时通过仓储边界保留未来更换驱动或 PostgreSQL 的可能。
- 影响：新平台不再兼容 Node.js 18；参考虚谷应用保持原有 Node.js 18 兼容性且未被修改。

## D-008 版本子图规范化存储

- 状态：`accepted`
- 决策：项目保存指向 `published` 和 `draft` 的独立版本指针；作战单元、路线、任务、依赖和战线按版本使用独立表存储。
- 原因：确保项目隔离、关系约束、事务更新和未来发布/回滚不依赖单一巨型 JSON。

## D-009 服务端摘要会话与内存 CSRF

- 状态：`accepted`
- 决策：使用随机 Cookie 会话，数据库只保存 token 摘要；Cookie 为 HttpOnly、SameSite=Strict，CSRF token 只进入页面内存。
- 原因：避免将可重放凭据暴露给 JavaScript 或 Web Storage，并同时覆盖会话固定、跨站写请求和浏览器后退缓存风险。
- 影响：首版采用 30 分钟空闲与 8 小时绝对过期；HTTPS 部署必须启用 Secure Cookie。

## D-010 平台壳只使用本地固定组件

- 状态：`accepted`
- 决策：Phase 2 使用仓库内语义 HTML/CSS/JavaScript，不引入远程 UI registry、CDN、项目提供的组件或内联可执行资源。
- 原因：平台与项目内容边界必须清晰，且当前阶段不应提前形成任意代码低代码入口。

## D-011 多项目平台沿用 Xugu 桌面界面骨架

- 状态：`accepted`
- 决策：桌面端以 Xugu 稳定应用的白色顶部导航、暖色指挥背景、左目标/右战况 Hero 和纵向章节卡片为平台基线；多项目能力只增加项目入口、切换器、筛选和管理控件。
- 原因：用户明确要求新平台与 Xugu Agentic Group Schedule 界面基本一致，通用 SaaS 侧栏会破坏已有认知和迁移连续性。
- 影响：响应式仍作为兼容回退，但不能反向主导桌面信息结构；Phase 3 固定模块继续在同一 Xugu 视觉框架中扩展。

## D-012 项目表现文案由模板和术语配置驱动

- 状态：`accepted`
- 决策：项目详情的顶部标题、Banner、当前状态提示、事实标签、模块标签和新建摘要由项目模板与结构化术语配置决定，不使用全平台硬编码的 Xugu 文案。
- 原因：平台需要管理不同类型项目，同时保留 `xugu-agentic-group` 作为首个 Xugu Agentic Group Schedule 作战项目的界面连续性。
- 影响：标准项目使用团队、任务、里程碑和交付物语言；作战项目使用作战单元、行动任务、战役节点和战果语言。配置只能选择固定预设，不得提供项目级页面代码。

## D-013 版本化目录与固定九模块渲染边界

- 状态：`accepted`
- 决策：模板以不可变的 `templateId@version` 目录发布，模块数据以显式 `schemaVersion` 与 allowlist `viewVariant` 交换；服务端只注册九种模块，浏览器只使用仓库内固定 renderer map。
- 原因：同一平台需要表达 Xugu 作战项目和标准项目差异，同时阻止项目数据、材料或未来 LLM 输出选择组件路径或执行页面代码。
- 影响：模板可配置术语、主题、字段、状态、模块顺序/启停和已批准视图；未知模板、类型、Schema、视图和可执行内容全部失败关闭。模块配置只写草稿，发布仍留给后续审核发布阶段。

## D-014 项目证据采用本地确定性检索与显式授权

- 状态：`accepted`
- 决策：首版材料使用项目隔离的本地对象目录、SQLite 关系与 FTS5；证据只有在处理成功、属于当前代际且获得项目问答授权时才进入检索。provider 默认禁用，只接收受控上下文且不得调用工具。
- 原因：单服务器内部试用需要无外部密钥也可完整验证，并必须把跨项目泄漏、提示注入、伪造引用和处理失败控制在可重复测试的事务边界内。
- 影响：材料原件和运行产物不进入 Git；可选扫描/OCR/PDF 工具通过有界适配器接入。问答只能返回 allowlist 引用并保持只读，更新意图在 Phase 4 仅作为元数据。

## D-015 生成任务锁定证据清单且提案独立验证后保存

- 状态：`accepted`
- 决策：每个 generation task 在创建时锁定 `projectId`、当前发布版本、同模板材料、当前提取代际、证据 ID/哈希和 Schema；provider 只能返回相同 envelope 下的结构化增量。服务端在持久化前独立执行 Schema、项目/证据、模板字段、目标、语义、日期、依赖 DAG、重复和版本冲突校验。
- 原因：模型输出和材料正文都不可信，只有服务器拥有授权、当前版本、固定模块和事务边界；把锁定输入、provider 调用和验证提案分离可以确定性阻断跨项目引用、旧证据、stale base 与模型越权。
- 影响：仅完整通过的 pending proposal 与规范化 item/evidence 关系原子保存；失败任务保留稳定状态、attempt、Token/成本聚合且不留部分提案。generation provider 配置与 chat 独立，默认禁用；Phase 5 没有任何 draft/published 写路径。

## D-016 审核决定独立保存且草稿合并采用 copy-on-write

- 状态：`accepted`
- 决策：提案项保持不可变，人工决定、编辑字段、说明与审核人保存到独立审核实体；合并从当前草稿复制新版本，应用所有接受项并完成完整图校验后才切换草稿指针。
- 原因：需要同时保留模型原建议、人工修订和可审计决定，并确保任一字段、关系或存储失败都不污染现有草稿。
- 影响：接受不等于合并，合并不等于发布；非法编辑在保存阶段重新验证，事务失败不产生部分版本或指针变化。

## D-017 发布创建新版本和草稿基线，回滚只走直接前驱

- 状态：`accepted`
- 决策：发布只复制当前草稿为新的不可变发布版本，并从其创建新的草稿基线；回滚只能指向当前发布事件记录的直接前驱。
- 原因：显式版本链比覆盖式更新更容易审计、恢复和隔离，并阻止客户端选择任意历史版本造成状态跳跃。
- 影响：发布/回滚必须由项目管理员或平台管理员确认，携带 CSRF，并写 `publication_events` 与追加式审计；提案不存在直达发布路径。

## D-018 SQLite 备份使用一致快照并离线恢复

- 状态：`accepted`
- 决策：运行备份使用 SQLite `VACUUM INTO` 产生一致文件；恢复前验证 quick check、外键和最低迁移版本，恢复要求应用离线并先保存目标数据库备份。
- 原因：直接复制 WAL 数据库文件可能得到不一致快照，在线覆盖运行数据库会破坏连接与事务状态。
- 影响：备份和恢复通过服务端脚本执行，运行数据库、上传原件和备份文件均不进入 Git。

## D-019 作战单元生命周期采用版本化状态，不做物理删除

- 状态：`accepted for Phase 7`
- 决策：作战单元/团队新增、归档和退出都作为带证据的版本化提案进入审核；归档和退出通过 `active / archived / exited` 生命周期状态表达，不从历史版本中物理删除。
- 原因：作战单元承载任务、甘特、战线、成果和证据链，物理删除会破坏历史发布版本、审计和材料来源解释。
- 影响：归档或退出前必须校验未完成任务、依赖、战线和甘特引用；如仍有活跃引用，提案必须同步迁移、关闭或归档相关任务，否则阻止接受或合并。

## D-020 发布前运维采用本地 request trace 与脱敏诊断包

- 状态：`accepted for Phase 7`
- 决策：每个 HTTP 请求、后台材料任务、生成任务、审核合并和发布事件都生成或继承 request/trace ID；未知异常和后台失败保存脱敏堆栈、错误指纹和关联上下文，并提供管理员诊断包。
- 原因：准备对外发布时，用户可上报一个稳定编号，管理员能定位堆栈、作业、提案和发布上下文，同时不能泄露 Cookie、CSRF、密钥、材料正文或模型提示词。
- 影响：普通用户只看到报障编号；平台管理员或授权项目管理员才能查看诊断信息。产品内测试中心必须覆盖 trace、错误事件和诊断包权限边界。

## D-021 路线图采用多视图工作台，卡片移动仍走结构化提案

- 状态：`accepted for Phase 8`
- 决策：路线模块不再只承担单一曲线节点展示，而是提供固定、可切换的活动路线图、阶段卡片板、作战单元进度和依赖网络四种投影。活动路线图采用以时间列为主的活动、目标、任务表达；阶段卡片板采用状态泳道与可拖拽任务卡。所有视图均读取同一受控版本化数据并保持对象深链。
- 原因：用户需要同时看到战略阶段、多作战单元分支、执行进度和材料更新后的待审核变化；当前曲线主图适合概览但不适合承载密集的多任务协作，也不能把点击结果隐藏到页面底部。
- 影响：路线、单元、任务和 proposal item 必须有一致的稳定 ID、选中态和就地详情。拖拽、状态推进、负责人/日期调整不得绕过 `ChangeProposal`、审核、copy-on-write 草稿合并与人工发布；这不是任意看板编辑器，也不允许项目注入前端代码。
