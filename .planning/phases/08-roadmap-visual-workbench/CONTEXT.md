# Phase 8：路线图可视化工作台与卡片化审核

状态：`implemented`
最后更新：2026-07-21

## 用户已确认的目标

将当前“战役路线”从单一曲线节点概览，升级为同时支持战略表达和执行管理的固定视觉工作台。借鉴 Aha 的时间列活动路线图和 Trello 的卡片/泳道管理原则，但使用平台自己的视觉与信息架构，不复制其品牌或页面。

材料上传后的新增、更新、归档和关键缺失，应成为审核员第一眼可见的审核卡片；卡片集中呈现更新建议、证据、字段差异、缺失属性、风险和审核动作，不能把结果散落或隐藏在页面底部。

## 固定视图

1. **活动路线图**：按日期/阶段划分时间列。每列包含阶段或里程碑、目标（Goals）、来自多个作战单元的任务卡；日期与阶段使用细连接线关联。当前阶段清晰选中，分支工作必须在正确时间列/阶段表达。
2. **阶段卡片板**：选定阶段的任务按 `待确认 / 进行中 / 待审核 / 已完成` 等状态泳道排列。卡片显示标题、作战单元、负责人、日期、证据数、关键缺失或风险。用户可拖拽卡片，但拖拽只能形成受控提案或审核动作。
3. **作战单元进度**：以作战单元为入口，展示其覆盖的阶段、任务、完成度、风险、材料状态和可跳转对象。
4. **依赖网络**：继续使用固定依赖图，作为跨单元、跨阶段阻塞关系的定位入口。
5. **项目泳道（`?view=swimlane`，第 5 视图）**：以分形生命周期（事前/事中/事后，由 `stage.state` 派生）为顶带；主泳道沿任务时间轴铺排阶段（阶段起点即拆解锚点·项目锚点），副泳道为各作战单元的甘特任务条（同单元并行子任务按 track 着色），收口锚点由 `closures.between` 两端阶段中点生成；`?stage=`/`?unit=`/`?task=`/`?anchor=` 深链正交。该视图为 D-022 分形作战模型的纯投影可见层，不改隔离与数据边界。

五种视图由相同的项目版本图、稳定对象 ID 和受控 DTO 驱动；切换视图不能写入版本，也不能让项目配置提供 HTML、CSS、JavaScript 或 SVG。

## 交互契约

- 路线节点、分支、作战单元、任务和审核卡片都必须有可见可点击性、键盘访问、选中态、就地详情和可复制深链。
- 选择对象后详情在当前视觉工作区或右侧检查器打开；不允许仅滚动到很远的页面底部展示结果。
- 从活动路线图选择阶段应筛选阶段卡片板；从卡片选择任务应同步路线、作战单元进度和依赖网络的对象焦点。
- 多作战单元、多任务及跨阶段依赖必须显示为受控关系，不以拥挤交叉线、无意义圆点或主路径装饰物替代。

## 受控写入与审核边界

- 卡片拖拽、状态移动、负责人调整、日期调整和作战单元转移都不是直接编辑 `draft` 的能力。
- 客户端创建带 `projectId`、当前版本、目标 ID、字段增量、操作者、来源交互和必要证据的 `ChangeProposal` 或审核编辑请求。
- 服务端复用模板 Schema、权限、任务图、日期、证据、状态转换、重复和版本冲突校验；仅审核接受后，才由既有 copy-on-write 合并进入新草稿。
- `published` 仍只能由人工发布动作更新；AI、拖拽和客户端都没有直达路径。

## 材料到审核卡片的目标流程

1. 管理员上传材料并选择更新模板。
2. readiness 显示必要属性是否齐全；关键缺失阻止高影响生成。
3. generation 生成受证据约束的 `ChangeProposal`，不写版本。
4. 系统按 proposal item 生成审核卡片：新增任务、更新任务、新增单元、归档/退出单元、指标更新等。
5. 审核员在卡片上查看证据定位、原值/建议值、字段差异、置信度、风险、关键缺失与 trace/request ID，并接受、编辑后接受或驳回。
6. 接受项按现有事务机制合并到 `draft`，随后人工发布。

## 视觉约束

- 桌面端继续保持 Xugu 的白色顶部导航、暖色指挥背景与作战语言；不能退回深色左侧栏的通用 SaaS 外壳。
- 使用浅蓝灰工作画布、深海军蓝文字、蓝色主操作、浅绿目标卡、浅橙关键缺失/风险卡；卡片采用紧凑信息密度、清晰层级、轻边框和柔和阴影。
- 避免主路线波浪线、巨大空白、不可点击的悬浮 Tag、没有上下文的圆点、密集难读的依赖交叉线，以及将明细隐藏在页面底部。
- 只借鉴 Aha/Trello 的信息组织原则，不使用其商标、Logo 或直接复制布局。
