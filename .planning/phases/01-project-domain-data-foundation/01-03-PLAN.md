# Plan 03: Project API, Compatibility, and Phase Verification

## Objective

Expose the imported data through project-scoped APIs, preserve the read-only legacy public entry, and close Phase 1 with full verification and truthful documentation.

## Must-haves

- `GET /api/projects/:projectId/public` reads only that project's published pointer.
- `GET /api/projects/:projectId/draft` reads only that project's draft pointer and is explicitly documented as pre-auth Phase 1 behavior.
- Unknown/malformed project IDs return deterministic 404/400 responses and never fall back to another project.
- `GET /api/public` temporarily aliases only `xugu-agentic-group` published data.
- API tests prove two-project namespace isolation.
- `npm run verify` covers migrations, import/export, API smoke tests, sensitive/runtime-file checks, and the reference read-only assertion.
- Result/state/handoff documents describe only implemented Phase 1 capability.

## Tasks

### 1. HTTP application

- Build a dependency-injected Node HTTP handler with JSON error responses, no-store headers, request size limits where relevant, and clean shutdown.
- Add `/health`, `/api/projects`, project public/draft routes, and `/api/public` compatibility route.
- Add no mutating, publish, proposal-review, material, authentication, or UI routes in this phase.

### 2. API tests

- Start the server against a temporary database and dynamically assigned port.
- Test health, project list, Xugu public/draft content, compatibility equality, unknown IDs, malformed IDs, and method handling.
- Import a second synthetic project and prove responses do not mix title, units, tasks, or versions.

### 3. Unified verification

- Run syntax checks and all Node tests.
- Create an isolated temporary database, migrate, import, export, and compare canonical data.
- Start an isolated server and request the project API and compatibility API.
- Fail if runtime databases or sensitive local files are tracked.
- Capture the reference application's Git status, HEAD, and seed checksum before/after and require them to remain unchanged.

### 4. Documentation and project memory

- Correct the reference-project path in project instructions/docs.
- Record the Node/SQLite decision and repository/version boundary.
- Update architecture and migration documentation to match actual schema/API.
- Update RESULT with only implemented capabilities and explicit remaining scope.
- Update PROCESS, STATE, and HANDOFF with commits, verification evidence, risks, and next phase.
