# 项目决策

## D-001 独立新项目，不在稳定应用上直接大改

- 状态：`accepted`
- 决策：平台在独立目录和独立 Git 仓库开发；现有虚谷作战地图保持稳定，只作为迁移来源和验收样本。
- 原因：平台化涉及数据模型、权限、存储和 UI 壳重构，直接在稳定应用上施工会增加回退和数据风险。

## D-002 平台—项目—作战单元三级结构

- 状态：`accepted`
- 决策：平台管理多个项目；每个项目内部管理多个作战单元或团队。

## D-003 固定模块加模板，不做任意代码低代码

- 状态：`accepted`
- 决策：低代码能力来自固定模块、版本化 Schema、项目模板和结构化数据；LLM 不生成或执行页面代码。

## D-004 LLM 只生成增量提案

- 状态：`accepted`
- 决策：LLM 输出带 `projectId`、`baseVersion` 和证据的 `ChangeProposal`；管理员审核后合并到草稿，人工发布。

## D-005 首版采用 SQLite

- 状态：`accepted`
- 决策：首版单服务器使用 SQLite 提供事务、索引和迁移；多机部署需求出现后再评估 PostgreSQL。

## D-006 当前虚谷项目是首个迁移项目

- 状态：`accepted`
- 决策：稳定 ID 为 `xugu-agentic-group`，迁移必须保持七个作战单元、路线、任务、甘特和成果语义。

## D-007 使用 Node.js 内置 SQLite 接口

- 状态：`accepted`
- 决策：平台最低运行时提高到 Node.js 24.15，使用内置 `node:sqlite` `DatabaseSync`。
- 原因：保持单服务器部署简单，避免原生 npm 数据库驱动的编译和交付差异，同时通过仓储边界保留未来更换驱动或 PostgreSQL 的可能。
- 影响：新平台不再兼容 Node.js 18；参考虚谷应用保持原有 Node.js 18 兼容性且未被修改。

## D-008 版本子图规范化存储

- 状态：`accepted`
- 决策：项目保存指向 `published` 和 `draft` 的独立版本指针；作战单元、路线、任务、依赖和战线按版本使用独立表存储。
- 原因：确保项目隔离、关系约束、事务更新和未来发布/回滚不依赖单一巨型 JSON。

## D-009 服务端摘要会话与内存 CSRF

- 状态：`accepted`
- 决策：使用随机 Cookie 会话，数据库只保存 token 摘要；Cookie 为 HttpOnly、SameSite=Strict，CSRF token 只进入页面内存。
- 原因：避免将可重放凭据暴露给 JavaScript 或 Web Storage，并同时覆盖会话固定、跨站写请求和浏览器后退缓存风险。
- 影响：首版采用 30 分钟空闲与 8 小时绝对过期；HTTPS 部署必须启用 Secure Cookie。

## D-010 平台壳只使用本地固定组件

- 状态：`accepted`
- 决策：Phase 2 使用仓库内语义 HTML/CSS/JavaScript，不引入远程 UI registry、CDN、项目提供的组件或内联可执行资源。
- 原因：平台与项目内容边界必须清晰，且当前阶段不应提前形成任意代码低代码入口。

## D-011 多项目平台沿用 Xugu 桌面界面骨架

- 状态：`accepted`
- 决策：桌面端以 Xugu 稳定应用的白色顶部导航、暖色指挥背景、左目标/右战况 Hero 和纵向章节卡片为平台基线；多项目能力只增加项目入口、切换器、筛选和管理控件。
- 原因：用户明确要求新平台与 Xugu Agentic Group Schedule 界面基本一致，通用 SaaS 侧栏会破坏已有认知和迁移连续性。
- 影响：响应式仍作为兼容回退，但不能反向主导桌面信息结构；Phase 3 固定模块继续在同一 Xugu 视觉框架中扩展。

## D-012 项目表现文案由模板和术语配置驱动

- 状态：`accepted`
- 决策：项目详情的顶部标题、Banner、当前状态提示、事实标签、模块标签和新建摘要由项目模板与结构化术语配置决定，不使用全平台硬编码的 Xugu 文案。
- 原因：平台需要管理不同类型项目，同时保留 `xugu-agentic-group` 作为首个 Xugu Agentic Group Schedule 作战项目的界面连续性。
- 影响：标准项目使用团队、任务、里程碑和交付物语言；作战项目使用作战单元、行动任务、战役节点和战果语言。配置只能选择固定预设，不得提供项目级页面代码。
