# Phase 7 Context：材料更新可靠性、作战单元生命周期与发布运维

状态：`accepted for planning`
日期：2026-07-20

## Locked scope

- 上传材料后，系统必须先根据更新模板给出关键内容覆盖诊断，再允许生成或明确降级生成。
- 诊断输出必须区分 `ready`、`warning`、`blocked`，并列出缺失字段、影响模块、能否继续、建议补充材料。
- 六类更新模板都要有确定性 readiness 规则；高影响字段和事实更新缺少证据时不得进入可接受提案。
- 作战单元/团队支持新增、归档、退出。归档和退出不是物理删除，而是版本化生命周期变化。
- 作战单元生命周期变化必须带证据、生效日期和原因；若仍有未完成任务、依赖、甘特泳道或战线引用，必须同步关闭、迁移或归档，否则阻止审核接受或合并。
- 当前发布版保留历史可追溯性；已归档/退出单位在当前模块默认折叠或标记，历史版本中仍完整存在。
- 每个 HTTP 请求、材料处理任务、生成任务、审核合并、发布回滚都要有可关联的 request/trace ID。
- 未知异常和后台失败必须保存脱敏错误事件，包含堆栈指纹、可检索堆栈、用户/项目/路由/作业上下文和相关审计 ID。
- 前端普通用户只看到报障编号；管理员可查看诊断页、错误详情、关联作业和导出诊断包。
- 产品内提供管理员自检与回归用例中心，测试运行不污染真实项目发布版。

## Non-goals

- 不做无审核自动发布。
- 不做任意历史版本分支编辑或物理删除作战单元。
- 不把模型提示词、材料正文、Cookie、CSRF、密钥或上传原件写入错误事件。
- 不引入外部 APM/SaaS 依赖；Phase 7 使用本地 SQLite、日志文件和仓库内测试夹具。
- 不把完整成员目录、外部身份提供商、PostgreSQL 或多服务器部署放入本阶段。

## Current evidence

- 当前 `proposalTemplates` 允许 `units` 的 `create/update`，但不允许 `delete`，也没有 `status/effectiveDate/reason` 生命周期字段。
- `applyUnit` 明确拒绝 unit delete，更新仅覆盖 name/objective/owner。
- `validateTaskGraph` 已能阻止任务引用不存在的作战单元，但尚未判断归档/退出单位上的未完成任务或战线引用。
- 生成前上下文会检查材料 ready、提取代际、模板一致、generation 授权和证据存在，但没有模板级关键内容覆盖诊断。
- HTTP 错误目前返回 `code + message`，未知异常写 `console.error`；还没有 requestId、结构化错误事件、堆栈查询或诊断包。
